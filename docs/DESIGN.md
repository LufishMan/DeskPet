## 1. 產品原則
1. **安靜陪伴**：預設不出聲、不彈窗、不搶焦點。
2. **輕量**：目標是自身 CPU 平均 < 1%（含 WebView 子程序）；記憶體主程序 < 40 MB、含 WebView 子程序合計 < 150 MB（工作集），以免干擾自己的數值。量測方式見 §2。
3. **隱私**：所有資料都存在本機，不連網。只讀取整體 CPU 和記憶體數值，**不讀取程序名稱、視窗內容、鍵盤輸入，也不讀取全域滑鼠位置**；只處理使用者在寵物或玩具視窗上的點擊、拖曳和游標停留。
4. **隱藏機制**：品種判定、體型分數、性格這類數值都不直接顯示，讓玩家自己觀察和摸索。
5. **最小權限、不觸碰其他程式、看起來就是普通軟體**：任何平台都不需要管理員或特殊權限，不改動其他程式或視窗，也不做任何容易被誤認為惡意程式的行為。細節見 §14。

## 2. 系統架構
```
┌──────────── Rust 後端（背景常駐）────────────┐
│ 休眠偵測 ──┐                                   │
│ CPU 取樣  ─┼─► 養分引擎 ─► 成長狀態機 ─┐      │
│ 記憶體取樣 ┴─► 心情引擎 ────────────────┼─► SQLite 存檔
│                活力 / 飢餓引擎 ─────────┘      │
└──────────────────────────┬────────────────────┘
                           ▼ 事件（tick / 進化 / 心情變化 / 系統事件）
┌──────────── 前端：與寵物同尺寸的透明置頂小視窗 ────┐
│ 像素渲染（Canvas 2D，整數倍放大、nearest-neighbor）│
│ 行為 AI：科別基底 ＋ 個體性格 ＋ 親密度 ◄── 使用者互動 │
└──────────────────────────────────────────────────┘
```

| 模組 | 實作方向 |
|---|---|
| 系統數值 | **直接呼叫作業系統 API，不使用 `sysinfo`**（它在 Windows 上可能開啟所有程序的 handle，包括 `lsass.exe`，見 §14.5）。Win：整體 CPU 用 `GetSystemTimes`，自己用 `GetProcessTimes(GetCurrentProcess())`；macOS：`host_statistics64`、`task_info(mach_task_self())`；Linux：`/proc/stat`、`/proc/self/stat` |
| 休眠偵測 | 監聽系統的睡眠和喚醒事件（Win：`PowerRegisterSuspendResumeNotification`，回呼形式，不需要視窗；macOS：`NSWorkspace` 睡眠通知；Linux：logind `PrepareForSleep`）。另外比對取樣之間的實際時間差（超過 3 個取樣間隔就視為休眠，丟棄未完成的 tick），作為保險 |
| 記憶體壓力 | macOS：memory pressure（`kern.memorystatus_vm_pressure_level`）；Win：`GlobalMemoryStatusEx.dwMemoryLoad`＋分頁檔使用量；Linux：`/proc/pressure/memory`（PSI）或 MemAvailable |
| 自身用量 | Win：啟動時建立 Job Object 並把自己加入，WebView2 子程序會自動歸入同一個 Job；用 `QueryInformationJobObject(JobObjectBasicAccountingInformation)` 取得**本程式全部程序**的 CPU 時間，不需要列舉或開啟其他程序。macOS / Linux：只扣主程序（WebView 程序不是子程序），誤差靠低幀率控制 |
| 存檔 | SQLite（`rusqlite`，bundled），每個 tick 寫入一次，查詢一律參數化。路徑**明確指定**為 §14.5 B 的資料夾，不使用 Tauri 預設的 identifier 路徑；WebView2 的使用者資料夾也指定到 `%LOCALAPPDATA%\DeskPet\WebView2\` |
| 前端 | 原生 TypeScript + Vite，**不用 UI 框架、不用 PixiJS**（WebGL 會拉高 GPU 程序用量，也多一個相依套件）。Canvas 2D 繪製：動作中 10 fps、待機 4 fps，視窗隱藏時完全停止繪製 |
| 視窗 | **和寵物同尺寸的小視窗**，寵物移動時移動整個視窗；透明、無邊框、永遠置頂。邏輯畫布 40×44（寵物 32×32 置底置中，上方留圖示泡泡的空間），依縮放倍率 ×2～×4。玩具和倉鼠囤糧各自使用一個獨立小視窗，**同時最多 3 個小視窗**。**不使用全螢幕透明覆蓋層** |

|---|---|---|

| 稀有色盤（約 5%） | 稀有變種，例如白化、黑化 | 罕見 |

| 科 | 蛋紋暗示 | 品種 |
|---|---|---|
| 貓科 | 條紋 | 米克斯（虎斑）、英國短毛貓、美國短毛貓、布偶貓、暹羅貓、波斯貓 |

## 4. 養分機制（CPU）

### 4.1 Tick
- 一個 tick 是 **N = 5 分鐘**。每 10 秒取樣一次，tick 結束時取平均，並扣掉本程式自己的用量。
- 只要電腦沒有休眠或待命，每個 tick 都算活躍並結算。螢幕鎖定、使用者離開座位也照樣計算。

### 4.2 熱量換算（依上班常態校準）

| CPU 平均 | 熱量 / tick |
|---|---|
| < 5% | 2 |
| 5–15% | 4 |
| 15–35% | 6 |
| 35–65% | 8 |
| > 65% | 10 |

- **標準速率**：5 熱量 / tick，相當於一般文書和瀏覽器工作。
- **標準工作週**：8 小時 × 5 天 × 12 tick = 480 tick，約 **2,400 熱量**。
- **每日上限**：720 熱量（標準日的 1.5 倍）。達到上限之後，寵物進入「吃飽睡覺」狀態，**這段時間的 tick 不結算熱量，也不計入體型判斷**。
- **閒置小睡**：CPU 連續 1 小時（12 個 tick）低於 5% 之後，寵物進入「閒置小睡」，比照吃飽睡覺**不結算熱量、不計入體型**，直到出現一個 CPU ≥ 5% 的 tick 為止。小睡中的 tick 仍算活躍（活躍定義不變）。休眠造成 tick 中斷時，閒置計數重來。目的是讓 24 小時不關機的電腦不會因為夜間和週末閒置而把寵物拉瘦。

### 4.3 成長階段與門檻
進入下一階段需要**同時**符合兩個條件：累積到門檻熱量，並且在目前階段待滿最短天數。

| 階段轉換 | 所需熱量 | 最短天數 | 標準耗時 |
|---|---|---|---|
| 蛋 → 幼年（孵化） | 2,400 | 7 天 | 約 1 週 |
| 幼年 → 少年 | 3,600 | 7 天 | 約 1.5 週 |
| 少年 → 成年 | 4,800 | 10 天 | 約 2 週 |
| 成年 → 傳承 | 4,800 | 14 天 | 約 2 週以上 |

- 最短天數是為了保住「1～2 週一次變化」的節奏。這是針對電腦 24 小時不關機的情況：每天都會達到熱量上限，沒有天數限制的話，3～4 天就會變化一次。
- **等待期**：熱量已達門檻、但天數還沒到時，寵物進入等待期。等待期比照「吃飽睡覺」處理：**tick 不結算熱量，也不計入體型判斷**；超出門檻的熱量不會帶到下一階段。蛋在等待期會出現裂痕和晃動（§11.1）。
- 從蛋到成年在標準節奏下大約 4.5 週。
- 所有數值都集中放在 `balance.toml`，方便之後調整。

## 5. 隱藏小階段與體型
- 每個大階段切成 **4 個隱藏檢查點**，在門檻的 25%、50%、75%、100% 處。
- 判斷方式（吃飽睡覺、閒置小睡、等待期的 tick 不計入）：每通過一個檢查點，記錄這一段的 ratio：
  ```
  預期 tick 數 = (門檻 / 4) / 5
  ratio = 這一段實際計入的 tick 數 / 預期 tick 數
  ```
  ratio 小代表吃得快（每個 tick 熱量高）、偏胖；ratio 大代表吃得慢、偏瘦。
- 體型 = 最近 4 個檢查點 ratio 的**加權平均**，權重由舊到新是 1、1、2、3；不足 4 個時只用現有的（權重對齊最新的檢查點）。檢查點紀錄跨階段延續，新寵物沒有紀錄時為標準。
- 對應 5 級體型（再扣掉飢餓扣分，見 §6）：

  | 加權平均 ratio | < 0.70 | 0.70～0.85 | 0.85～1.20 | 1.20～1.50 | > 1.50 |
  |---|---|---|---|---|---|
  | 體型 | 很胖 | 胖 | 標準 | 瘦 | 很瘦 |
- 實際效果：體型穩定反映「近期的平均 CPU 強度」，5 級都會出現，不會因為時間累積而衝到極端。v0.6 初版用 −1／0／+1 評分加總，模擬結果是只要習慣穩定就會衝到極端，所以改成這個做法。
- M1 模擬結果（每 tick 平均熱量 → 體型）：文書 5 → 標準（ratio ≈ 1.0）；24 小時不關機（有閒置小睡）→ 標準（≈ 1.08）；重度運算 8 → 很胖（≈ 0.63）；輕度使用 2.8 → 很瘦（≈ 1.8）。

## 6. 活力 / 飢餓機制
| 情況 | 效果 |
|---|---|
| 電腦連續 4 個日曆日都在關機或休眠（涵蓋週末加一天假） | 不受影響 |
| 第 5 天起，每多一天 | 活力 −1；從第 6 天起每 2 天，飢餓扣分 `hunger_penalty` +1 |
| 最低狀態 | 活力 1、很瘦：動作變慢、常常趴著、互動反應變少。**不會死亡** |
| 恢復 | 回來後每個活躍日活力 +1；每通過一個檢查點，飢餓扣分 −1 |

- **活力**共 5 級（1～5），新寵物從 5 開始。活力 ≤ 2 時，養分吸收 × 0.8，代表需要「養回來」。
- **活躍日**：當天至少有 12 個活躍 tick（約 1 小時）的日曆日。
- **飢餓扣分**直接從體型等級往下扣：顯示體型 = 依 body_score 對應的等級 − `hunger_penalty`，最低到「很瘦」。扣分另外存放，不改動檢查點紀錄，所以回來後會隨檢查點逐步回升。
- 離開天數在程式啟動或從休眠喚醒時，用 `last_active_date` 和今天的日期差回推一次結算。
- 這套機制使用日曆日，只負責懲罰「長期不在」；成長和體型仍然只看活躍 tick。

## 7. 心情機制（記憶體）
- 不直接用「記憶體使用率 %」，因為系統快取會讓這個數字常年偏高。改用各平台的**記憶體壓力**指標（見 §2）。
- 每 10 秒取樣一次，並做 EMA 平滑（時間常數約 10 分鐘）。

| 壓力 | 心情 | 像素表現 |
|---|---|---|
| 低 | 愉悅 | 跳躍、音符符號、主動玩耍 |
| 中 | 普通 | 正常待機 |
| 高 | 緊張 | 冒汗符號、來回踱步 |
| 極高 | 沮喪 | 縮成一團、烏雲符號、不理人 |

- 心情會影響養分吸收：愉悅 ×1.1、普通 ×1.0、緊張 ×0.9、沮喪 ×0.75。
- 上班環境常同時開很多瀏覽器分頁或 Teams，門檻要實測校準，避免寵物長期沮喪。

## 8. 個性系統

寵物的個性分兩層：
- **科別基底**：同一科的共同習性，例如貓偏獨立、狗偏黏人。
- **個體性格**：每隻寵物孵化時各自用機率決定，所以同一科、同一品種的寵物個性也會不同。

### 8.1 性格軸
每隻寵物有 4 條性格軸，數值都是 0～100：

| 性格軸 | 低 ← → 高 |
|---|---|
| 黏人度 | 傲嬌、獨立 ← → 黏人、愛撒嬌 |
| 活潑度 | 慵懶、愛睡 ← → 好動、停不下來 |
| 膽量 | 膽小、易受驚 ← → 大膽、不怕生 |
| 好奇心 | 謹慎、宅 ← → 好奇、愛探險 |

### 8.2 產生方式（孵化時決定）
```
性格值 = clamp( 科別基底 + 品種修正 + 常態亂數(平均 0, 標準差 15), 0, 100 )
```
- 每條軸**各自獨立**抽籤。
- 標準差 15 代表每條軸大約 1/3 的個體會偏離科別基底 15 分以上（往高、往低各約 1/6）。所以會自然出現黏人的貓、傲嬌的狗這類「反差個體」。

**科別基底：**

| 科 | 黏人 | 活潑 | 膽量 | 好奇 |
|---|---|---|---|---|
| 貓科 | 35 | 50 | 55 | 70 |
| 犬科 | 80 | 70 | 60 | 60 |
| 鼠科 | 45 | 75 | 25 | 75 |
| 倉鼠科 | 40 | 60 | 30 | 55 |
| 熊科 | 55 | 25 | 65 | 40 |

**品種修正（範例）**：柴犬黏人 −15、黃金獵犬黏人 +10、哈士奇活潑 +15、布偶貓黏人 +15、波斯貓活潑 −15、暹羅貓活潑 +10、貓熊活潑 −10。

### 8.3 特殊癖好（quirk）
每個癖好都用**各自獨立的機率**判定，所以一隻寵物可能一個都沒有，也可能同時有好幾個：

| 癖好 | 機率 | 表現 |
|---|---|---|
| 戲精 | 6% | 被點擊時誇張倒地、受驚反應加倍 |
| 夜貓子 | 6% | 傍晚以後比較有精神，早上常打瞌睡 |
| 吃貨 | 8% | 吃東西的動畫比較多，游標停在身上時以為是食物、湊過去聞 |
| 愛乾淨 | 6% | 常常理毛、洗臉 |
| 愛唱歌 | 4% | 心情好時冒出音符 |
| 路痴 | 4% | 走路偶爾撞牆、繞圈 |

### 8.4 性格怎麼影響行為
性格**只影響行為，不影響成長數值**（養分、體型、成長速度）。這樣不同性格的寵物不會有強弱之分，平衡也比較好調。

| 性格軸 | 影響範例 |
|---|---|
| 黏人度 | 回應點擊的機率、被摸時的熱情程度、喚醒時迎接的熱情程度 |
| 活潑度 | 主動行為的頻率、睡眠時間的比例 |
| 膽量 | 被連點時被嚇到的門檻、被拖曳時的反應 |
| 好奇心 | 去視窗邊緣探索的頻率、看到玩具的反應速度 |

### 8.5 揭露方式
- 飼養期間不顯示任何性格數值或提示，讓使用者自己觀察。
- **只在寵物退休、進入回憶相簿時**揭露一句性格描述，例如「黏人又膽小的柴犬・吃貨」。

## 9. 互動系統

### 9.1 設計原則
- **一律由使用者主動發起**：寵物不會要求使用者照顧，也不會因為沒互動而受懲罰。
- **短**：每次互動的動畫都在 3 秒內結束，不打斷工作。
- **用圖示表達**：一律用像素圖示泡泡（愛心、音符、問號、Zzz），不顯示文字，干擾比較少。
- **頻率可調**：設定中可調整「活潑度」（低／中／高），專注模式下完全不主動互動。

### 9.2 操作方式
| 操作 | 意義 | 範例反應（實際反應會依科別和性格調整） |
|---|---|---|
| 單擊 | 摸摸 | 黏人的寵物冒愛心；傲嬌的寵物可能無視，或甩尾走開 |
| 連點 | 搔癢 | 打滾；戲精直接倒地 |
| 長按 | 抱住 | 貓可能掙扎，狗會搖尾巴 |
| 拖曳後放開 | 抱起來移動 | 貓落地站穩；倉鼠縮成球滾一下；膽小的會躲起來 |
| 滑鼠停在寵物上方 | 注視 | 抬頭看游標、歪頭 |
| 右鍵選單 | 功能選單 | 玩具、相簿、專注模式、隱藏、設定 |

- 所有操作都只來自寵物或玩具視窗本身收到的滑鼠事件。**不輪詢全域游標位置**，所以游標離開這些視窗後，寵物不知道游標在哪裡。

**各科的招牌行為（科別習性，再由個體性格調整強弱）：**

| 科 | 習性 | 招牌行為 |
|---|---|---|
| 貓科 | 傲嬌、獨立 | 點擊有機率被無視；趴在使用中視窗的標題列（需開啟 §9.4）；在螢幕上緣曬太陽；被拖曳時炸毛 |
| 犬科 | 忠誠、黏人 | 被摸時搖尾巴、坐好等下一次摸摸；電腦從休眠喚醒時熱情迎接；丟球會撿回來 |
| 鼠科 | 膽小、機靈 | 被連點或拖曳時受驚，躲到螢幕邊緣；動作細碎快速 |
| 倉鼠科 | 囤積、貪吃 | 把養分具象化成瓜子，囤在角落；兩頰鼓起；跑滾輪（CPU 高時跑得更快） |
| 熊科 | 慵懶、食量大 | 閒置小睡（§4.2）時打瞌睡；電腦從休眠喚醒時伸懶腰；動作慢；會做出推視窗的動作（**只有視覺效果，視窗不會真的移動**） |

### 9.3 玩具（從右鍵選單取出，一次只能放一個）
| 玩具 | 最適合的科別 | 玩法 |
|---|---|---|
| 毛線球 | 貓科 | 拖曳拋出，寵物去追 |
| 逗貓棒 | 貓科 | 使用者拖著逗貓棒晃動，寵物跳起來撲 |
| 球 | 犬科 | 拋出去，寵物撿回來放到拋出的位置 |
| 骨頭 | 犬科 | 寵物叼著、啃一陣子 |
| 滾輪 | 倉鼠科、鼠科 | 放在角落，寵物進去跑（CPU 越高跑越快） |
| 竹子／樹枝 | 熊科 | 貓熊啃竹子，袋熊挖土 |

- 每種寵物都可以玩所有玩具，只是對適合的玩具反應比較熱烈。
- 玩具是一個獨立的小視窗（16×16 × 縮放倍率）。拖曳、拋出都是對玩具視窗本身操作；寵物追的是**玩具視窗的位置**（本程式自己的視窗），不需要讀取游標。倉鼠的囤糧堆也用同樣的方式實作。

### 9.4 環境互動（**預設關閉**；只讀取視窗位置，不改動任何視窗）
- 定時讀取「使用者正在用哪個視窗」很像員工監控軟體，所以預設關閉，由使用者在設定中開啟。
- 開啟後，也只在寵物執行這類動作時才讀取，頻率最多每 2 秒一次，而且只讀取位置和大小。

開啟後的行為：
- 沿著工作列或 Dock 上緣散步。
- 跳到目前使用中視窗的標題列上坐著；視窗移動或關閉時，寵物「掉下來」並做出落地動作。
- 躲在螢幕邊緣或視窗邊緣，只露出半個頭。

### 9.5 系統事件反應
| 事件 | 反應 |
|---|---|
| 電腦從休眠喚醒 | 依黏人度做迎接：狗衝過來，貓伸懶腰看一眼，熊打哈欠 |
| CPU 突然飆高 | 興奮進食、流汗 |
| 記憶體壓力升高 | 依心情表現（§7） |
| 每天第一次開機 | 打招呼動作 |
| 傍晚下班時段 | 收拾、揮手（時段可以設定） |
| 休息提醒（**預設開啟**，可關閉） | 電腦每連續清醒 60 分鐘，寵物就伸一次懶腰，提醒起來動一動。用計時器實作，不監聽輸入；休眠後重新計時。間隔可以設定 |

### 9.6 隨機小事件
低機率發生的小動畫，讓寵物看起來有生命感：追蝴蝶、打噴嚏、做夢說夢話（冒出 Zzz 和小圖示）、看窗外發呆、找到小東西。

### 9.7 親密度（隱藏數值）
- 每次互動增加親密度，**每天有上限**，不需要長時間陪玩。
- 親密度**不會因為沒互動而下降**，符合「安靜陪伴」原則。
- 親密度越高，會解鎖更多行為：狗叼小禮物來、貓慢慢眨眼、倉鼠把瓜子分給使用者。
- 親密度會讓黏人度慢慢上升，最多 +10。所以再傲嬌的寵物，養久了也會變得比較親近。

### 9.8 開發優先順序
| 版本 | 內容 |
|---|---|
| **M4 首批** | 操作方式（§9.2）、系統事件反應（§9.5）、每科一種代表玩具（毛線球、球、滾輪、竹子） |
| 後續版本 | 其餘玩具（§9.3）、環境互動（§9.4）、隨機小事件（§9.6）、親密度解鎖行為（§9.7） |

## 10. 上班友善功能
- **老闆鍵**：一個全域快捷鍵就能隱藏或顯示（只註冊快捷鍵，不監聽鍵盤輸入）。
- **專注模式**：寵物縮到螢幕角落、停止主動互動，但照常結算數值。
- **全螢幕 / 簡報時自動隱藏**：Windows 用 `SHQueryUserNotificationState` 判斷，不需要列舉視窗；macOS 的全螢幕 App 位在獨立的桌面空間，寵物視窗本來就不會出現，不需要額外偵測。
- **預設靜音**，沒有系統通知。只有進化時有低調的像素動畫提示，可以關閉。
- **休息提醒**預設開啟（§9.5）。
- **登入時自動啟動預設關閉**，需要使用者在設定中主動開啟（理由見 §14 R1）。開啟後常駐系統匣。

## 12. 傳承機制
1. 成年後達到傳承條件（§4.3），寵物身邊出現一顆新蛋。
2. 使用者選擇（右鍵選單或點擊新蛋時出現的選擇，選擇前寵物照常生活）：
   - **延續血脈**：新蛋繼承親代的科別，世代數 +1。
   - **開新血脈**：新蛋的科別完全隨機（5 科機率相同，也可能抽到原本的科），開始新的血脈，世代數從 1 起算。
3. 親代退休，進入「回憶相簿」，保留成長履歷：品種、各階段的日期、體型變化曲線，並揭露性格描述（§8.5）。
4. 新蛋接手，從頭開始培養。

**遺傳規則：**

| 項目 | 規則 |
|---|---|
| 科別 | 延續血脈時**繼承親代**；開新血脈時重新隨機 |
| 科內品種、毛色、稀有變種 | 重新隨機 |
| 性格、癖好 | 重新隨機 |
| 體型、心情、親密度 | 不遺傳，全部歸零 |

- 一次只能養一隻；新蛋出現時，親代同時退休。
- 回憶相簿同時作為圖鑑，顯示已收集到的品種；相簿依血脈分組。

## 14. 資安風險評估

### 14.1 結論
這個程式的資料敏感度很低，攻擊面也小：不連網、不讀取輸入或其他程式的內容、不需要特殊權限。

**最大的風險不是被入侵，而是在公司被擋下或被誤判成惡意程式。**「未簽章」「免安裝」「開機自動啟動」「透明且置頂的視窗」「定時讀取系統數值」「全域快捷鍵」這幾個特徵組合在一起，很像惡意程式的行為模式。設計上要刻意避開這些特徵，並且做到讓 IT 容易稽核。

因為**不簽章、不開源、也不主動報備**，IT 沒有任何事前資訊可以判斷這個程式。所以策略是：**讓程式的實際行為乾淨到沒有可疑之處，並且在 IT 來查的時候一看就懂**（§14.5）。R1、R2 是最需要持續注意的兩項。

### 14.2 權限盤點（設計目標：任何平台都不需要特殊權限）
| 項目 | Windows | macOS | 需要管理員或特殊權限？ |
|---|---|---|---|
| 整體 CPU 和記憶體 | `GetSystemTimes`、`GlobalMemoryStatusEx` | `host_statistics64`、`sysctl` | 否 |
| 本程式自己的 CPU 用量 | 自己建立的 Job Object：`QueryInformationJobObject` | `task_info(mach_task_self())` | 否（**不列舉、不開啟其他程序**） |
| 滑鼠 | 只處理寵物和玩具視窗本身收到的事件 | 同左 | 否（**不輪詢全域游標位置、不使用 hook**） |
| 休眠與喚醒事件 | `PowerRegisterSuspendResumeNotification` | `NSWorkspace` 通知 | 否 |
| 其他視窗的位置（選用，預設關閉） | `GetWindowRect` | `CGWindowListCopyWindowInfo`（只讀取 bounds） | 否（**不讀取視窗標題**，所以 macOS 不需要螢幕錄製權限） |
| 全螢幕偵測 | `SHQueryUserNotificationState` | 不需要（全螢幕 App 位在獨立桌面空間） | 否 |
| 老闆鍵 | `RegisterHotKey` | Carbon `RegisterEventHotKey` | 否（**不使用鍵盤 hook**，所以 macOS 不需要輔助使用權限） |
| 開機自動啟動（選用，預設關閉） | `HKCU\...\Run` | `SMAppService` | 否 |
| 網路 | 不使用 | 不使用 | — |

**刻意不做的事**：移動或改變其他視窗、讀取視窗標題或內容、監聽鍵盤滑鼠、讀取全域游標位置、截圖、列舉其他程序、存取網路。

| R9 | 不連網所以無法自動更新，漏洞修補比較慢 | 中 | 低～中 | 攻擊面本來就小；WebView 由作業系統負責更新；發佈頁提供安全公告；存檔格式有版本號，換新版很容易 | 低 |
| R10 | macOS 未簽章的程式無法執行或被隔離 | **高** | 中 | Apple Silicon 至少要 ad-hoc 簽章（`signingIdentity: "-"`）才能執行。macOS 15 起已經不能用右鍵「打開」繞過，使用者要到「系統設定 → 隱私權與安全性 → 強制打開」。有 MDM 管理的公司 Mac 可能完全無法執行 | 中～高 |
| R11 | 使用者改系統時間作弊 | 中 | 極低 | 單機遊戲，影響只有自己；偵測到時間倒退時，該段時間不結算就好 | 可接受 |

### 14.4 開發階段的資安檢查表
- [ ] Tauri capabilities 只開放自訂指令，所有指令都在後端驗證參數。
- [ ] CSP 嚴格設定；不使用 `eval`，不載入遠端腳本。
- [ ] Windows 連結參數 `/DEPENDENTLOADFLAG:0x800`，啟動時設定 DLL 搜尋路徑。
- [ ] 確認不列舉其他程序、不讀取視窗標題、不使用輸入 hook、不呼叫 `GetCursorPos`。
- [ ] 確認所有寫入（含 WebView2 使用者資料）都在 `%LOCALAPPDATA%\DeskPet\` 內。
- [ ] CI 執行相依套件稽核；發佈檔附 SHA-256 和 minisign 簽名。
- [ ] 提供「給 IT 的說明文件」。
- [ ] 每次發佈前，用 Windows Defender 和 VirusTotal 掃描，確認沒有誤判。（注意：上傳到 VirusTotal 的檔案會公開，只上傳要正式發佈的版本。）

### 14.5 低疑慮執行策略（不簽章、不報備）

前提：未簽章的新程式一定會被 EDR 記錄成「罕見的未知程式」，這一點無法避免。目標是：**被記錄，但沒有任何會升級成警示的行為**；萬一 IT 來查，能在幾分鐘內確認沒問題。

**A. 行為準則（程式碼審查時逐項檢查）**

| 類別 | 必須 | 禁止 |
|---|---|---|
| 程序 | 只有本程式和 WebView2 的子程序 | 啟動 cmd / PowerShell / 腳本；列舉或開啟其他程序（特別是 `lsass.exe`）；注入、讀取其他程序的記憶體 |
| 網路 | 完全不連線 | 回傳數據、檢查更新、載入 CDN 資源 |
| 檔案 | 只寫入自己的資料夾（含 WebView2 使用者資料） | 寫出執行檔、修改或刪除自己、寫入系統資料夾 |
| 登錄檔 / 持續執行 | 只有使用者開啟自動啟動時，在 `HKCU\...\Run` 寫入一個值 | 排程工作、服務、其他登錄位置 |
| 輸入與畫面 | 用 `RegisterHotKey` 註冊老闆鍵；只處理自己視窗收到的滑鼠事件 | 鍵盤或滑鼠 hook、輪詢全域游標、截圖、讀取視窗標題或內容 |
| 視窗 | 寵物、玩具、囤糧的小視窗（同時最多 3 個）；系統匣圖示常駐；視窗標題是產品名稱 | 全螢幕透明覆蓋層；隱藏自己 |
| 執行檔 | 一般編譯產物；完整的版本資訊（產品名稱、說明、版本、發行者名稱）和圖示 | 加殼（UPX 等）、混淆、仿冒系統程式名稱 |

**B. 放置位置（README 建議）**

| 項目 | Windows | macOS |
|---|---|---|
| 程式 | `%LOCALAPPDATA%\Programs\DeskPet\DeskPet.exe`（一般「只安裝給目前使用者」的軟體慣用位置） | `~/Applications/DeskPet.app` |
| 存檔 | `%LOCALAPPDATA%\DeskPet\` | `~/Library/Application Support/DeskPet/` |
| 避免 | 直接從 `Downloads`、`Temp`、`AppData\Roaming` 執行 | 直接從「下載項目」執行 |

**C. 建立信譽**
- 少發版，目標每月最多一版。每個新版本都是新的 hash，信譽要重新累積。
- 每次發佈前用 Microsoft Defender 掃描。如果被誤判，以「軟體開發者」身分向 Microsoft Security Intelligence 提交誤判申訴（免費，不需要簽章）。
- 只把正式版本上傳到 VirusTotal 檢查。
- 發佈頁和程式的「關於」頁都顯示版本與 SHA-256，讓任何人都能比對。

**D. 讓 IT 看得懂（被動透明）**
- zip 內附 README：程式做什麼、不做什麼、使用的 API 清單（§14.2）、資料存放位置、如何完整移除。
- 程式內的「關於」頁顯示相同的說明。
- 提供一鍵「完全移除」：刪除存檔資料夾，並移除自動啟動設定。

**E. 被擋下時的原則**
- 如果被 AppLocker、WDAC、MDM 或防毒軟體擋下，**就停止使用**。不改檔名、不換資料夾、不關閉防毒，文件中也不提供任何繞過方法。這些做法違反公司政策，也正是會引發調查的行為。
- 使用前請自行確認公司的軟體使用規範。

**F. 可行性評估**

| 環境 | 可行性 | 說明 |
|---|---|---|
| Windows，只有 Defender 或一般防毒 | 高 | 第一次執行會出現 SmartScreen，按「其他資訊 → 仍要執行」 |
| Windows，有 EDR（例如 Defender for Endpoint、CrowdStrike） | 中～高 | 會被記錄成罕見程式；只要遵守 A 項準則，通常不會升級成警示 |
| Windows，啟用 AppLocker / WDAC 白名單 | 不可行 | 未簽章又未核准的程式一定會被擋 |
| macOS，未受 MDM 限制 | 中 | 第一次要到「系統設定 → 隱私權與安全性 → 強制打開」 |
| macOS，MDM 限制未識別的開發者 | 不可行 | 一定會被擋 |

結論：**Windows 是這個方案的主要目標平台**；macOS 能用，但在公司環境被擋下的機會比較高。

## 15. 發佈：免安裝版

### 15.1 各平台形式
| 平台 | 形式 | 說明 |
|---|---|---|
| Windows | 單一 `.exe`（或 zip 內含 exe） | 依賴系統內建的 **WebView2**：Win11 和已更新的 Win10 都有。缺少時要顯示友善的提示訊息，而不是直接閃退。C 執行階段靜態連結，不需要另外安裝 VC++ 可轉散發套件 |
| macOS | `.app` 放在 zip 裡，ad-hoc 簽章 | Mac 本來就是「拖曳即用」，等同免安裝 |
| Linux | AppImage | 單一檔案，賦予執行權限就能使用 |

### 15.2 發佈原則
- **不做程式碼簽章、不提供安裝版、不開源、不主動報備**；執行策略見 §14.5。
- 發佈頻率：每月最多一版（§14.5 C）。
- 發佈內容：程式檔、`SHA256SUMS`、minisign 簽名檔，以及兩份說明文件：
  - **使用者說明**：如何驗證檔案、如何允許執行。
  - **給 IT 的說明**：程式做什麼、不做什麼、使用的 API 清單（§14.2）。
- 未來如果要在公司內大規模推廣，再重新評估簽章。低成本的選項有 Azure Trusted Signing。

### 15.3 免安裝版的實作考量
| 考量 | 說明 | 對策 |
|---|---|---|
| **存檔位置** | 免安裝版習慣把資料放在程式旁邊，但程式可能被放在唯讀位置；macOS 從下載資料夾執行時，還會被系統搬到隨機的唯讀路徑（App Translocation） | 一律存在使用者資料夾的固定位置（§14.5 B），不寫在程式旁邊 |
| **存檔遺失** | 使用者可能直接刪掉或搬動資料夾 | 提供 JSON 格式的「匯出 / 匯入存檔」（§14 R6）；每天自動保留最近 7 份備份 |
| **開機自動啟動** | 沒有安裝程式幫忙設定 | 預設關閉。使用者開啟後由程式自己設定，不需要管理員權限：Win 寫入 `HKCU\...\Run`；macOS 用 `SMAppService`。程式換位置時要自動更新路徑 |
| **更新** | 沒有安裝程式，也不連網 | 手動下載新版覆蓋即可，存檔不受影響。存檔格式有版本號（`schema_version`），支援自動遷移 |
| **重複開啟** | 同一份存檔被兩個程式同時寫入 | 使用單一執行個體鎖（single instance） |

## 17. 待討論事項
1. 官方發佈管道：建議另外建立一個**只放執行檔的公開 GitHub 儲存庫**，原始碼仍放在私有儲存庫。公司網路通常允許連到 GitHub，Releases 頁面也能清楚顯示版本和 hash。待確認。
2. 數值平衡（熱量門檻、體型判斷、心情門檻）等 M1 模擬器完成後再一起校準。
3. 「開新血脈」時是否保留舊血脈的世代紀錄可以回顧：目前規劃是保留在相簿中，依血脈分組（§12）。
4. **輕度使用者成長太慢**：模擬中平均每 tick 2.8 熱量的使用者，各階段要 11／19／26／24 天，超出「1～2 週」的目標。現代電腦做文書工作的 CPU 常常低於 5%，所以這可能是常態而不是少數。等 `sys` 取樣器完成後，先在實際上班環境收集一週 CPU 分布，再決定要不要調整熱量級距。
